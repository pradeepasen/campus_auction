You are building a hackathon project in about 5 hours: a campus auction web app. Build it phase by phase, run it after each phase, and keep the app working at all times. Currency is Indian rupees (₹).

The story
It is the last day of final semester exams. Seniors are leaving campus within a week and leaving behind cycles, calculators, books and electronics. Juniors need them, but today they are sold in chat groups where the fastest person wins and the price is a guess. Build the place where campus competes fairly for these items so every item finds its next owner. Every item is its own auction, and different items close at different times.

Tech stack
Next.js (App Router) + TypeScript, SQLite with Prisma, Tailwind CSS + shadcn/ui, simple session login with hashed passwords. Poll the server every 2 seconds for live updates. Photos upload to /public/uploads. Secrets in .env only. Provide npm run seed (4 demo users; 12 to 15 listings across cycle, calculator, books, electronics and others, with closing times from 2 minutes to 3 days; some bids) and a README with run steps and demo logins.

Core principles
ALL rules are enforced on the server in one shared function layer. The UI, the auto-bidder, and the AI assistant must all call the same functions. Never trust the browser clock; use server time.
Placing a bid runs inside a single database transaction so simultaneous bids cannot both win.
A background tick on the server runs every second to close auctions whose time has passed. Every read also checks closing, so an auction is never shown as open after its time.
Everything about bidding is public: all bids, bidders, amounts, times, and auto-bid maximums. Never expose emails, passwords, phone numbers or any other account details anywhere, including to the AI assistant.
BASICS (build these first, all mandatory)
Listings
A seller creates a listing with: title, category (cycle, calculator, books, electronics, other), description, condition (new, like new, good, fair, poor), photos (up to 5), starting price, minimum bid increment, and a closing date and time for that item.
Validate: closing time in the future, price and increment greater than zero.
A seller can edit or cancel a listing. After the first bid, starting price, increment and closing time are locked; text and photos can still be edited. Cancelling records the outcome "Cancelled by seller" and notifies bidders.
A seller cannot bid on their own listing.
Browsing
Search by keyword (title and description). Filters: category, condition, price range (on current price), and closing soon (within 1 hour, within 24 hours). Filters combine.
Each auction page shows: item details, photos, current leading bid and leader, the FULL bid history (bidder, amount, time), and its own live countdown.
Home page shows active auctions by default, with a tab for closed ones with their outcomes.
Bidding
A bid must be at least the starting price (first bid) or current price plus the minimum increment.
Bids after the closing time are rejected with a clear message.
Every bid is stored with bidder, amount and time and shown in public history.
Closing and sale
Statuses: ACTIVE, CLOSED_UNSOLD, PENDING_APPROVAL, RESERVED, COMPLETED, REJECTED, CANCELLED, PICKUP_FAILED.

When closing time passes, bidding stops. The highest valid bid becomes the provisional winner (status PENDING_APPROVAL). If nobody bid, status is CLOSED_UNSOLD.
The seller approves or rejects the winning price. Approve means RESERVED for the winner. Reject means REJECTED.
After approval, a confirmed campus handover (confirmed by the seller; the winner can also confirm) sets COMPLETED. The seller can mark PICKUP_FAILED if pickup does not happen.
Rejection, seller cancellation and failed pickup each show a clear, distinct outcome label on the listing and for the winner.
Notifications
In-app notification center with unread count. Events: outbid, you are provisional winner, new bid on your item, auction closed, approval needed, approved or rejected, item reserved, handover completed or failed, wishlist match, question answered, closing time extended.
A settings toggle lets the student allow browser notifications (Web Notifications API). The same alerts then appear as browser pop-ups when the app is open in a background tab. Handle the permission being denied gracefully.
KEY FEATURES (build after the basics, in this order)
1. Last-minute extensions
If a valid bid arrives in the last 30 seconds before closing, set the closing time to 60 seconds after that bid. This can repeat. Everyone watching sees the new countdown on the next poll, and a "closing time extended" notice and notification appear.

2. Automatic bidding
A buyer sets a public maximum for an auction (for example ₹1,800 for a cycle). The app bids for them only as much as needed to keep them in the lead, never above the maximum.

Show maximums publicly on the auction page.
If a manual bid is below the leader's maximum, the system immediately places an auto-bid for the leader at min(leader's max, manual bid + increment) and records it as an auto-bid in the public history.
If a manual bid reaches or exceeds the leader's maximum, the new bidder leads and the old leader is notified as outbid.
If two auto-bidders compete, they escalate by the increment until the lower maximum is passed; the higher maximum wins at (lower maximum + increment), capped at its own maximum. On equal maximums the earlier one wins.
All of this runs in the same transaction as the triggering bid and respects closing time and extensions.
A buyer can raise or remove their maximum before closing.
3. Questions before bidding
On each auction, buyers can ask questions and the seller answers them publicly on the page, so one answer helps everyone.

Spam control: only logged-in buyers (not the seller) can ask; max 3 unanswered questions per user per auction; at most 1 question per 30 seconds; max 300 characters; block exact duplicates; while typing, show similar existing questions to avoid repeats; the seller can hide a question; no new questions after the auction closes.
Show answered questions first; notify the seller of new questions and the asker when answered.
4. Never miss what you need
A student can save a "want" such as keywords "scientific calculator", category calculator, max price ₹400. It is stored in the database and persists when the student is offline. When a matching listing is created (or edited to match), create a notification for the student immediately, so they see it the next time they open the app. Show a "My wants" page where they can add, pause and delete wants.

5. AI assistant tab
A chat tab where a student says things like "find me a cycle under ₹2,000" and gets a straight answer, and can ask the assistant to bid for them. Use a Claude or Gemini API with tool calling, key in .env. If no key is configured, fall back to a simple keyword and price parser so the tab still works.

Tools: search_listings(query, category, max_price), get_listing(id), propose_action(listing_id, type, amount). Tools return only public listing data. They must never return anyone's email, password or account details, and the assistant must refuse to reveal them.
The assistant NEVER acts without the student's go-ahead. propose_action creates an AssistantProposal that the student must approve with a button in the UI. Only then does the server place a bid or set an auto-bid maximum.
The student's agreed limit is stored with the proposal. The server enforces it on execution regardless of what the model says, and rejects anything above it or on a different listing.
The assistant follows all normal bidding rules; it gets no special powers.
